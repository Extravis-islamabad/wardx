# Tenancy key management (design, for review)

Status: **draft for review. Nothing here is implemented yet.**
Scope: how WardX encrypts tenant data once it is multi-tenant (MonetX style: a parent control-plane
database plus one database per tenant), how keys rotate without manual re-encryption, and how
backups are encrypted and restored one tenant at a time.

## 1. Goals and threat model

| # | Threat | Requirement |
|---|---|---|
| T1 | Parent DB dump stolen | No tenant secret, and no usable tenant key, can be recovered from it. |
| T2 | One tenant DB dump stolen | No secret recoverable without the master key; nothing about other tenants in it. |
| T3 | Tenant A's admin or key compromised | Tenant B unaffected: different key, different DB, AAD binds every blob to its tenant. |
| T4 | Backup media stolen | Encrypted end to end; useless without the master key. |
| T5 | Operator restores tenant A | Nothing of tenant B is decrypted, loaded or exposed during the restore. |
| T6 | Key suspected compromised | Rotate on demand. Old data is re-wrapped in the background, not re-entered by hand. |
| T7 | Master key provider unavailable | Fail closed: the vault reports sealed, nothing is decrypted with a fallback key. |
| T8 | Tenant offboarded | Crypto-shred: destroying its keys makes its data, including backups, unrecoverable. |

Non-goals: protecting secrets from a fully compromised running WardX process (it holds unwrapped
keys in memory by design), and side channels on the host.

## 2. Key hierarchy

```
Master key (MK)          in an HSM / KMS / TPM; never leaves it (file only in dev)
  └─ wraps → Tenant KEK (TKEK), one active version per tenant, per purpose
       ├─ vault   → wraps a data key (DEK) per secret version → AES-256-GCM secret
       ├─ backup  → wraps a DEK per backup archive            → AES-256-GCM stream
       └─ files   → wraps a DEK per session recording          → AES-256-GCM stream
  └─ wraps → Platform KEK (PKEK): control-plane secrets (parent-DB MFA seeds, LDAP bind
             passwords held in the parent, signing-key private halves)
```

- **MK.** One per installation (or per region). Only *wrap* and *unwrap* (or KMS `Encrypt`/`Decrypt`
  / `GenerateDataKey`) cross the provider boundary. Identified by `mk_id` (provider + key + version).
- **TKEK.** 256-bit random key per tenant, per purpose, per version. Generated by the provider
  (`GenerateDataKey`) where it can, otherwise from `os.urandom` in-process, then wrapped at once.
  Purposes are separate keys rather than derived ones, so each can rotate and be destroyed on its own.
- **DEK.** A fresh 256-bit key per object, exactly as the vault works today
  (`src/vault/envelope.py`): the object is sealed with AES-256-GCM under the DEK, and the DEK is
  sealed under the TKEK.

**Associated data binds every layer to its place.** A blob copied anywhere else fails
authentication instead of decrypting:

| Layer | AAD |
|---|---|
| TKEK wrapped by MK | `wardx-tkek|v1|{tenant_id}|{purpose}|{version}` |
| DEK wrapped by TKEK | `wardx-dek|v1|{tenant_id}|{owner_type}:{owner_id}:{version}` |
| Secret under DEK | `{tenant_id}|{owner_type}:{owner_id}:{version}` |

Today's AAD has no tenant id. Adding it is what makes a ciphertext moved between tenant
databases fail even if someone also copied the key row.

## 3. Where each key lives

| Item | Location | Form |
|---|---|---|
| MK | HSM / KMS / TPM (dev: file, refused when `environment=production`) | never exported |
| TKEK | parent DB `platform.tenant_keys` | **wrapped by MK only**; plaintext only in process memory |
| DEK | tenant DB `vault.secrets.wrapped_dek` (and in backup and recording headers) | wrapped by TKEK |
| Secret | tenant DB `vault.secrets.ciphertext` | AES-256-GCM under DEK |

Keys are kept in the parent and data in the tenant DB on purpose. A tenant DB dump holds no
key material at all. A parent dump holds only MK-wrapped keys and no ciphertext. Decrypting
anything needs both, plus the MK provider.

```sql
-- parent DB
CREATE TABLE platform.tenant_keys (
    id           UUID PRIMARY KEY,
    tenant_id    UUID        NOT NULL REFERENCES platform.tenants (id),
    purpose      VARCHAR(16) NOT NULL CHECK (purpose IN ('vault','backup','files')),
    version      INTEGER     NOT NULL,
    state        VARCHAR(12) NOT NULL CHECK (state IN ('active','retired','destroyed')),
    mk_id        TEXT        NOT NULL,      -- which MK (and version) wrapped it
    wrapped_key  BYTEA,                     -- NULL once destroyed
    wrap_nonce   BYTEA,
    created_at   TIMESTAMPTZ NOT NULL,
    retired_at   TIMESTAMPTZ,
    destroyed_at TIMESTAMPTZ,
    UNIQUE (tenant_id, purpose, version)
);
-- exactly one active version per tenant and purpose
CREATE UNIQUE INDEX uq_tenant_keys_active ON platform.tenant_keys (tenant_id, purpose)
    WHERE state = 'active';
```

`vault.secrets.kek_id` stores the TKEK row id, so each DEK names the exact key version that wrapped it.

## 4. Master key providers

One small interface, with the provider chosen by config:

```python
class KeyProvider(Protocol):
    mk_id: str                                             # current wrapping key
    async def wrap(self, key: bytes, aad: bytes) -> WrappedKey: ...
    async def unwrap(self, wrapped: WrappedKey, aad: bytes) -> bytes: ...  # any mk_id it still holds
    async def generate(self, aad: bytes) -> tuple[bytes, WrappedKey]: ...  # GenerateDataKey or urandom+wrap
    async def health(self) -> ProviderHealth: ...
```

| Provider | Use | Notes |
|---|---|---|
| `pkcs11` | on-prem / air-gapped (banks, telco, government) | Thales Luna, Utimaco, Entrust nShield, YubiHSM 2; SoftHSM2 in CI. AES key-wrap (KWP) or AES-GCM in the HSM. |
| `aws-kms`, `azure-kv`, `gcp-kms` | SaaS and cloud installs | Envelope via `GenerateDataKey`/`Encrypt`. Encryption context = AAD. Multi-region keys for DR. |
| `tpm2` | single-appliance on-prem without an HSM | MK sealed to the TPM (optionally to PCRs). Bound to one machine, so it **must** be paired with an escrowed copy (Shamir M-of-N shares held by named officers) for DR and hardware replacement. |
| `file` | development and tests only | Today's `.wardx/kek.key` behaviour. Startup refuses it in production. |

**Failure behaviour.**
- Startup checks the provider. If the provider can't be reached, `/health/ready` reports the vault
  as sealed and secret routes return `503 vault_sealed`.
- Unwrapped TKEKs are cached in process memory for a configured TTL (default 15 minutes), so a
  short provider blip doesn't stop sessions. After that, WardX fails closed.
- No other key ever acts as a fallback.

## 5. Runtime flow

1. A request resolves its tenant: tenant middleware reads the JWT tenant claim, plus
   `X-Active-Tenant-Id` for platform operators with a grant.
2. The `KeyCache` returns that tenant's active TKEK for the purpose. On a miss, it loads the
   wrapped row from the parent DB and unwraps it through the provider with the tenant-bound AAD.
3. The vault service seals or opens with the tenant-bound AAD and records the TKEK id on the row.
4. The API, gateway and scheduler each hold their own cache. A process never holds keys for
   tenants it hasn't served. Cached keys are dropped on rotation (a `NOTIFY tenant_keys` from the
   parent DB) and at TTL expiry.
5. Unwrapped keys are never logged, serialised, returned by any API, or written to disk. They
   live in `bytearray`s that are cleared when evicted (best effort in Python; documented as such).

## 6. Rotation without manual re-encryption

Every rotation is a background job: resumable, idempotent and audited. Nobody re-enters
secrets, and secret ciphertexts never change. Only the small wrapped keys above them are
re-wrapped.

**MK rotation** (scheduled, for example yearly, or on demand):

1. The provider creates a new MK version.
2. A job re-wraps every `tenant_keys` row: unwrap with the old version, wrap with the new one,
   update `mk_id`. That's one row per tenant, purpose and version, so a few thousand rows at most.
3. The old MK version is disabled only when no row references it.

**TKEK rotation** (scheduled per tenant, on demand, or on suspected compromise):

1. Insert version N+1 as `active` and mark N `retired` in one transaction. New seals use N+1
   immediately.
2. The re-wrap job walks `vault.secrets WHERE kek_id = N` in batches (`FOR UPDATE SKIP LOCKED`).
   For each row it unwraps the DEK with N, wraps it with N+1, and updates `wrapped_dek`,
   `dek_nonce` and `kek_id`, guarded by `WHERE kek_id = N`. That's 48 bytes per row; the secret's
   ciphertext is untouched. Recordings re-wrap their header DEK the same way.
3. Progress lives in `platform.key_rotations`: cursor, done/total and errors. A restarted job
   resumes from the cursor.
4. When no row references N, N stays `retired`. It is **destroyed** only after the backup
   retention window passes (see §7), because older backups still need it.
5. Every step is audited in the tenant's audit chain and the platform audit.

**On compromise:** rotate the TKEK as above, **and** queue a credential rotation (CPM, Phase 1)
for every account whose secret could have been read with it. Re-wrapping alone doesn't help if
the plaintext was already exposed.

**Migration from today's single env KEK:**
- Today `WARDX_VAULT_KEK` wraps DEKs directly, with no tenant id in the AAD.
- The tenancy migration creates tenant `default` with TKEK v1 and treats the env KEK as a legacy
  version.
- The same re-wrap job moves every DEK to v1, re-sealing each secret once with the new
  tenant-bound AAD. That pass touches ciphertext because the AAD changes, and it runs only once.
- After that the env KEK is removed. No manual step and no downtime: reads accept either version
  while the job runs.

## 7. Backups

**Per-tenant, per-purpose archives.**
- Each tenant's backup is its own archive: a `pg_dump` of the tenant DB plus its recordings.
  Tenants are never mixed in one archive.
- The archive is encrypted with a fresh DEK, wrapped by the tenant's **backup** TKEK.
- Streaming AES-256-GCM in 1 MiB chunks. Each chunk's nonce and AAD carry the chunk index and a
  final-chunk flag, so reordering, dropping or truncating chunks fails.
- The archive header holds the wrapped DEK, the backup TKEK id, the tenant id, the time and the
  schema version.

**Signed manifest.**
- Every archive has a manifest: tenant, time, sizes, SHA-256 of the ciphertext, every key id the
  data references (vault TKEK versions included), and the audit-chain head at backup time.
- The manifest is signed with the platform backup signing key (Ed25519, private half under the
  PKEK).
- A restore refuses an archive whose manifest doesn't verify.

**Key bundle.** Next to each archive goes that tenant's `tenant_keys` rows (all purposes, every
version the data references), **still MK-wrapped**. A tenant restore never needs another tenant's
key rows, or a parent DB restore.

**Parent DB backups** are encrypted the same way under a platform backup key. They contain only
MK-wrapped TKEKs, so on their own they reveal nothing.

**Restoring one tenant without exposing others:**

1. Verify the manifest signature and the archive hash.
2. Load the key bundle into `platform.tenant_keys` for **that tenant id only**. Rows already
   present are compared, never overwritten.
3. Unwrap the backup TKEK through the MK provider, decrypt the stream, and restore it into a
   **new, empty** tenant database. Swap it in only after verification.
4. Run audit-chain verification and a sample decrypt (open N random secrets) on the restored DB
   before going live.
5. Other tenants' databases, keys and caches are not read, decrypted or locked at any point. The
   restore tool takes a single `tenant_id` and has no "all tenants" mode.

**Retention and crypto-shred.**
- A retired TKEK version is destroyed (wrapped bytes erased, row kept as `destroyed`) only after
  every backup that references it has expired.
- Crypto-shred on offboarding destroys all versions at once. That makes the tenant's live data and
  all its backups unrecoverable, by design, and is confirmed by two platform admins.

**DR.**
- The MK must be reachable at the DR site: HSM replication, KMS multi-region keys, or the TPM
  escrow shares.
- Quarterly automated restore drills of one tenant into a scratch database, reported in the
  platform dashboard.

## 8. Other keys tenancy touches

| Key | Today | With tenancy |
|---|---|---|
| JWT signing | one HS256 secret | Asymmetric (Ed25519 / ES256) with `kid`. Tokens carry `tenant_id`; the private key is under the PKEK; rotation publishes the next key before switching. |
| Session recordings | plaintext asciicast files | Encrypted with the tenant's **files** TKEK (streaming GCM, as backups). The SHA-256 integrity hash stays in the audit chain. |
| MFA seeds, LDAP bind password | in the vault (single KEK) | Tenant users: tenant vault. Platform operators: PKEK. |
| Gateway SSH host key | file | Per gateway node, under the PKEK. |
| Audit-chain anchor (new) | none | Fixes the tail-truncation gap found by the security tests. A per-tenant Ed25519 key signs a checkpoint of the chain head (seq, hash, time) every N minutes and on shutdown. Checkpoints are stored in the **parent** DB and shipped to the SIEM. Verify then fails if the chain ends before the last signed checkpoint. |

## 9. Tests this design must pass

- `tests/security/test_cross_tenant.py` switches on: A's token with B's ids returns 404, A's lists
  never contain B's rows, and the `X-Active-Tenant-Id` spoof returns 403.
- A blob sealed for B fails to open with A's TKEK, and also with B's TKEK under A's AAD.
- Parent DB dump only, or tenant DB dump only: no secret recoverable (an automated "steal one
  side" test).
- Rotation: re-wrap job interrupted and resumed; reads correct throughout; old version retired
  and then destroyed; a backup taken before rotation still restores until retention ends.
- Restore A into a fresh DB while B is serving: B's latency and data are unaffected, and B's key
  rows are never read (query log assertion).
- Provider down: fail closed after the cache TTL; no plaintext fallback.
- The audit tail-truncation xfail turns into a pass, and its marker is removed.

## 10. Decisions needed in review

1. **Where users live.**
   - Option (a), parent DB like MonetX: platform operators and cross-tenant MSP staff are natural,
     and their MFA seeds go under the PKEK.
   - Option (b), each tenant DB: stronger isolation, and a tenant's people go with its backup.
   - Recommendation: **(a)**, to match MonetX, with tenant-scoped role grants.
2. **First HSM target** for on-prem: Thales Luna, Utimaco, or YubiHSM 2. SoftHSM2 will be used in
   CI regardless.
3. **TPM appliance mode:** acceptable only with Shamir escrow? Recommendation: yes, 3-of-5.
4. **Default backup retention** (it decides how long retired TKEKs live): 35 days, or set per tenant?
5. **Recordings encryption** in the tenancy step, or in Phase 2 with the new session protocols?
   Recommendation: tenancy step, since recordings already contain sensitive output today.
6. **Key generation:** in-HSM `GenerateDataKey` where available (recommended), or always
   in-process?
